# Task 08: Publish the test image (user action)

> **ЭТА ЗАДАЧА НЕ АВТОМАТИЗИРУЕТСЯ.** Она требует учётных данных мейнтейнера для DockerHub
> (`DOCKER_USERNAME` / `DOCKER_PASSWORD`), которых у агента нет и быть не должно. Агент, которому
> досталась эта задача, **не пытается** собирать и пушить образ, не ищет креденшелы в окружении и не
> подставляет свои. Он останавливается, выводит пользователю чеклист из «What to do» и ждёт
> подтверждения, что оба шага выполнены. Единственный допустимый «прогресс» без пользователя —
> подготовка команд и напоминание.

## Required Skills

Скиллы не загружаются — это инструкция пользователю, а не исполняемая агентом работа.
Задача описывает действие мейнтейнера; агент только передаёт её и фиксирует результат.

## Description

Мейнтейнер собирает тестовый образ `lesovsky/pgcenter-testing:0.0.11` из `testing/Dockerfile`
(в состоянии после Task 1 — с кластером PG 19), пушит его в DockerHub и **затем прогоняет этот образ на
неизменённом `develop`**.

Два шага, и порядок между ними существенный. Первый шаг — публикация — нужен просто потому, что оба
workflow (`default.yml`, `release.yml`) забирают образ из реестра по тегу: пока тега `0.0.11` в реестре
нет, бамп тега в ветке уронит каждый прогон CI на скачивании образа. Второй шаг — и есть смысл задачи.
Пересборка образа тянет **свежие минорные версии** пакетов PostgreSQL 14–18 и **заново собирает
CPAN-модули** (`Module::Build`, `Linux::Ethtool::Settings`) — то есть меняет окружение целиком, а не
только добавляет PG 19. Любая из этих посторонних подвижек может покрасить CI в красный по причинам,
не имеющим к фиче никакого отношения. Зелёный прогон нового образа на `develop` **без единой строчки
кода фичи** отделяет одно от другого: если прогон зелёный, образ чистый, и всякое последующее падение
CI однозначно принадлежит коду фичи. Если красный — разбираемся с образом здесь и сейчас, до того как
в ветку уедет хоть что-то из Go-задач.

Задача зависит **только от Task 1** — от содержимого образа. Ничего из того, что производят Go-задачи
(2–7), в сборку образа не попадает: образ содержит только Ubuntu, кластеры PostgreSQL, CPAN-модули и
два скрипта (`prepare-test-environment.sh`, `fixtures.sql`). Поэтому задача идёт своей веткой волн
параллельно Go-работе, а не после неё.

От неё, в свою очередь, зависят Task 9 и финальная QA-задача (Task 10): пока образ не опубликован,
workflow нельзя переключить на новый тег, а `testing/e2e.sh` не сможет прогнать порт 21919 — кластера
PG 19 в старом образе `0.0.10` просто нет. Это и есть Decision 4 тех-спека: `e2e.sh` и бампы тега в
обоих workflow едут одним мержем и только после публикации.

Требует учётных данных мейнтейнера для реестра — отсюда «user action» и отсутствие скилла и ревьюеров.

## What to do

**Шаг 1. Собрать и запушить образ.**

- Убедиться, что `testing/Dockerfile` и `testing/prepare-test-environment.sh` уже содержат изменения
  Task 1 (кластер PG 19, пин бета-канала) и что версия образа проставлена в двух местах Dockerfile:
  `LABEL version=` и строка `CMD ["echo", "pgcenter-testing <версия>: ..."]`. Комментарий-заголовок в
  шапке несёт **диапазон версий PostgreSQL**, а не версию образа — его тоже надо обновить (14-18 → 14-19),
  но это отдельная правка, не третье место с тегом.
- Собрать образ с тегом `0.0.11` из каталога `testing/`.
- Залогиниться в DockerHub под учёткой мейнтейнера и запушить тег.
- Убедиться, что тег виден в реестре и скачивается с чистой машины (`docker pull` без локального кэша).

**Шаг 2. Прогнать образ на неизменённом `develop` — ради этого всё и делается.**

- Взять `develop` **без единого изменения фичи**: ни бампа тега, ни правок `e2e.sh`, ни Go-кода задач
  2–7. Проверяется образ, а не фича.
- Прогнать в контейнере из нового образа тот же набор шагов, что и CI, **в том же порядке**. Важно:
  образ **намеренно не содержит ни Go-тулчейна, ни линтеров** — шапка Dockerfile прямо говорит
  «Go and lint tools are installed by CI, not bundled here», и workflow ставит их в контейнер на лету.
  Поэтому «просто запустить `make lint` внутри контейнера» не сработает: сначала окружение, потом проверки.
  Последовательность из `.github/workflows/default.yml`:
  1. чекаут `develop` смонтировать/скопировать в контейнер;
  2. поставить Go нужной версии (в workflow — распаковка тарбола в `/opt/go` и симлинки
     `go`/`gofmt` в `/usr/local/bin`);
  3. поставить линт-инструменты через `go install`: `golangci-lint`, `gosec`, `govulncheck` — и
     засимлинчить их из `~/go/bin` в `/usr/local/bin`, иначе `make lint` их не найдёт;
  4. `prepare-test-environment.sh` — поднять кластеры и загрузить фикстуры;
  5. пометить рабочую копию безопасной для git (`git config --global --add safe.directory …`) — иначе
     git-зависимые шаги ругаются на чужого владельца каталога;
  6. `make lint`;
  7. `govulncheck ./...`;
  8. `make test`;
  9. `make build`;
  10. `make install` — **не пропускать**: `e2e.sh` берёт `pgcenter` из PATH и работает под
      `set -euxo pipefail`, так что без установки прогон либо сразу падает, либо (если в PATH лежит
      старый бинарник) молча проверяет не тот код;
  11. `./testing/e2e.sh`.
- Прогон зелёный → образ чистый, можно разблокировать Task 9. Прогон красный → разобраться, что
  именно принесла пересборка (минорные версии PostgreSQL / пересобранные CPAN-модули / что-то в
  базовом образе), починить в образе и повторить оба шага. **Красный прогон не «принимается с
  оговоркой»** — вся ценность задачи в том, что после неё падения CI однозначно атрибутируются фиче.

**Шаг 3. Отчитаться.** Сообщить в чат: тег опубликован, прогон на неизменённом `develop` зелёный
(или что именно упало). Только после этого Task 9 и Task 10 считаются разблокированными.

## Verification Steps

Верификация — `user`: подтверждение мейнтейнера, автоматической проверки нет.

- **Публикация:** `docker pull lesovsky/pgcenter-testing:0.0.11` отрабатывает с машины, где образ
  локально не собирался. Ожидаемо: образ скачивается, `docker run … 0.0.11` печатает баннер с
  PostgreSQL 14-19.
- **Состав образа:** внутри контейнера после `prepare-test-environment.sh` слушают порты
  21914–21919 (шесть кластеров, включая PG 19 на 21919), фикстуры загружены.
- **Подготовка окружения:** в контейнере из `0.0.11` установлены Go и линт-инструменты (образ их не
  содержит — их ставит CI), `go version` и `golangci-lint --version` отвечают, `prepare-test-environment.sh`
  отработал без ошибок.
- **Главная проверка — чистота образа:** полный CI-набор на **неизменённом** `develop` в контейнере из
  `0.0.11`. Ожидаемо: `make lint`, `govulncheck ./...`, `make test`, `make build`, `make install`,
  `./testing/e2e.sh` — все зелёные. Никаких новых падений против того, что даёт `0.0.10` на том же коммите.
- **Чистота прогона:** `git status` в рабочей копии перед прогоном пуст, `git log` не содержит коммитов
  фичи. Если в прогоне участвовал бамп тега или правки `e2e.sh` — проверка недействительна, повторить.
- **Подтверждение:** пользователь сообщает «образ запушен, прогон зелёный». Без этого сообщения задача
  остаётся `in_progress`, а Task 9 и Task 10 — заблокированными.

## Details

**Files:** ни один файл репозитория этой задачей не меняется. `testing/Dockerfile` и
`testing/prepare-test-environment.sh` уже приведены в нужное состояние Task 1; здесь они только
собираются и публикуются.

**Dependencies:**
- **Task 1** — единственная зависимость. Даёт содержимое образа: бета-канал pgdg с пином (Decision 5a),
  пакеты `postgresql-19` / `postgresql-plperl-19`, PG 19 в шести циклах версий
  `prepare-test-environment.sh`. Пока Task 1 не закрыта, собирать нечего.
- **Go-задачи 2–7 в зависимостях отсутствуют намеренно** — ничего из их результата в образ не попадает,
  а шаг 2 требует ровно обратного: развёрнутого `develop` без их изменений.
- **Разблокирует:** Task 9 (бамп тега в обоих workflow + порт 21919 в `e2e.sh`) и Task 10 (финальная QA,
  которой нужен живой кластер PG 19).
- **Внешнее:** docker, учётная запись DockerHub мейнтейнера (`lesovsky`), сетевой доступ к
  `apt.postgresql.org` во время сборки.

**Edge cases:**
- **Пересборка красит CI в красный не из-за PG 19.** Ровно тот риск, ради которого существует шаг 2:
  свежие минорные PostgreSQL 14–18 и пересобранные CPAN-модули приезжают при любой пересборке. Разбор
  такого падения — часть этой задачи, а не Task 9.
- **Пин бета-канала не сработал** (Decision 5a): пакеты PG 14–18 в новом образе уехали на бета-сборки.
  Проверяемо изнутри контейнера — сравнить версии пакетов PostgreSQL 14–18 с теми, что в `0.0.10`.
  Это дефект Task 1, возвращается туда, а не «принимается».
- **Тег уже занят.** Если `0.0.11` по какой-то причине уже опубликован (черновая сборка), пушить поверх
  нельзя молча — CI закэширует неправильный слой. Либо перепроверить содержимое существующего тега,
  либо взять следующий номер и синхронно поправить его в Task 9 и `deployment.md` (Task 7).
- **Соблазн запушить бамп тега «заодно».** Прямо запрещено Decision 4: тег в `default.yml` /
  `release.yml` едет только в Task 9 и только после зелёного прогона.
- **Прогон на неизменённом `develop` в самом GitHub Actions.** Workflow берёт тег из закоммиченного
  `container:`, так что «прогнать новый образ на неизменённом develop» через CI без временной ветки не
  получится. Локальный прогон в контейнере из `0.0.11` — достаточный и предпочтительный вариант; если
  всё же используется временная ветка с одной строкой бампа тега, она **не мержится** и удаляется после
  прогона.

**Implementation hints (для мейнтейнера, не для агента):**
- Команды сборки и пуша — в `deployment.md`, раздел «Test Container»: сборка из каталога `testing/`,
  затем `docker push` того же тега.
- Список шагов для шага 2 брать из `.github/workflows/default.yml` — он и есть эталон того, что гоняет
  CI, в том же порядке: установка Go → установка линт-инструментов (`golangci-lint`, `gosec`,
  `govulncheck`) с симлинками в PATH → `prepare-test-environment.sh` → `git safe.directory` → lint →
  vuln → test → build → **install** → e2e. Шаги кэширования (`actions/cache`) при ручном прогоне
  просто пропускаются — они не влияют на результат, только на время.
- Образ пуст на тулчейн умышленно (шапка Dockerfile: «Go and lint tools are installed by CI, not
  bundled here»). Если `make lint` внутри контейнера падает с «команда не найдена» — это не дефект
  образа, а пропущенный шаг установки.
- Локальный запуск контейнера — по образцу `doc/development.md`, но с проброшенными портами
  21914–21919 (в самом doc список портов устаревший).
- `./testing/e2e.sh` в CI берётся **из чекаута**, а `prepare-test-environment.sh` — **из образа**. На
  шаге 2 это работает в нашу пользу: неизменённый `e2e.sh` не знает про порт 21919 и просто не трогает
  PG 19, проверяя ровно то, что нужно — что PG 14–18 не сломались.
- Креденшелы DockerHub нигде не логируются и не попадают ни в один файл репозитория.
