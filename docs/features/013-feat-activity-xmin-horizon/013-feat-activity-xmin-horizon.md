# User Spec: Activity screen — горизонт xmin и группировка параллельных воркеров

## Что делаем

Добавляем три колонки на существующий экран `activity` в `pgcenter top`: `leader`
(группировка параллельного запроса), `backend_xid` (писала ли транзакция) и `horizon_xacts`
(на сколько транзакций назад сессия держит горизонт xmin). Новых экранов и хоткеев не
появляется. Попутно чиним две структурные проблемы, на которые фича наступает: выбор режима
сортировки по разреженной колонке и пересчёт ширин колонок при смене версии внутри архива
(техдолг [021]).

Закрывает issue #148.

## Зачем

Сегодня экран `activity` не может ответить на вопрос **«какая сессия держит горизонт xmin и
тем самым не даёт vacuum убирать мёртвые строки»** — за этим приходится уходить в `psql`
посреди инцидента. Это ежедневный вопрос при расследовании раздувания таблиц.

Второе: на PG 13+ параллельные воркеры засоряют экран, и их нельзя привязать к лидеру —
тридцать строк одного запроса читаются как тридцать разных клиентов.

Третье: найдя держателя горизонта, DBA должен решить, можно ли его убить. Колонка `query`
на этот вопрос не отвечает и **активно вводит в заблуждение** — у сессии в
`idle in transaction` там лежит последний оператор, поэтому транзакция, сделавшая
`INSERT` → `SELECT` → простой, покажет невинный `SELECT`.

## Пользовательские истории

- Как DBA, расследующий раздувание таблицы, я хочу видеть, какая сессия держит самый старый
  горизонт xmin, чтобы понять, кто мешает vacuum убирать мёртвые строки.
- Как DBA во время инцидента, я хочу отличать параллельные воркеры от обычных бэкендов и
  видеть, к какому лидеру они относятся, чтобы не считать тридцать строк за тридцать клиентов.
- Как DBA, я хочу отличить писавшую транзакцию от только читающей, чтобы оценить цену
  `pg_terminate_backend`.

### Пользовательские сценарии

**Сценарий 1: найти держателя горизонта xmin**
1. Пользователь запускает `pgcenter top` и попадает на экран `activity`.
2. Сортирует по колонке `horizon_xacts` по убыванию.
3. Система ставит наверх сессию с самым старым горизонтом; сессии, не держащие горизонт
   (пустая ячейка), оседают вниз.
4. Пользователь смотрит соседнюю `xact_age` — сколько эта транзакция висит по времени.
5. Смотрит `state` — работает она или зависла в `idle in transaction`.
6. Смотрит `backend_xid` — писала ли она.
7. Результат: у пользователя есть полный ответ («держит горизонт 2.3M транзакций назад,
   транзакция открыта 40 минут, простаивает, ничего не писала») и основание для решения,
   убивать ли сессию.

**Сценарий 2: собрать группу параллельного запроса**
1. Пользователь видит на экране `activity` россыпь строк с `backend_type = parallel worker`.
2. Сортирует по колонке `leader`.
3. Система ставит лидера и всех его воркеров подряд одной группой — у них одинаковое
   значение `leader`.
4. Пользователь отличает лидера от воркера: у лидера `leader` равен собственному `pid`,
   у воркера — `pid` лидера.
5. Результат: тридцать строк читаются как один параллельный запрос, а не как тридцать
   клиентов.

**Сценарий 3: оценить цену убийства сессии**
1. Пользователь нашёл держателя горизонта (сценарий 1).
2. Смотрит `backend_xid`. Пусто — транзакция ничего не писала, `pg_terminate_backend`
   обойдётся дёшево.
3. Непусто — транзакция писала, убийство означает откат проделанной работы.
4. Результат: решение принято по факту, а не по обманчивому содержимому колонки `query`.

## Дизайн и интерфейс

pgcenter — терминальный TUI, поэтому «дизайн» здесь означает раскладку колонок таблицы.

### Страницы / экраны

- **`activity` (существующий экран, хоткей по умолчанию):** на PG 13+ таблица вырастает
  с 14 до 17 колонок. Новых экранов, хоткеев и пунктов меню не добавляется.
- **Экран `procpidstat` не затрагивается.** У него собственный запрос к `pg_stat_activity`,
  общего с `activity` — только хоткеи фильтров `I` и `A`.
- **Тоггла «скрыть параллельные воркеры» не делаем.** Он дублировал бы существующую
  машинерию фильтров ради узкого случая; группировка колонкой `leader` закрывает задачу.

### Раскладка колонок (PG 13+)

Порядок фиксируется дословно. На доступных версиях (PG 14–19) он сверяется с тем, что
вернул живой сервер; на PG 12 и 13 живых кластеров нет, там эта запись — единственный
источник истины.

| # | Колонка | Статус |
|---|---------|--------|
| 0 | `pid` | |
| 1 | `leader` | **новая** |
| 2 | `cl_addr` | |
| 3 | `cl_port` | |
| 4 | `datname` | |
| 5 | `usename` | |
| 6 | `appname` | |
| 7 | `backend_type` | |
| 8 | `wait_etype` | |
| 9 | `wait_event` | |
| 10 | `state` | |
| 11 | `backend_xid` | **новая** |
| 12 | `horizon_xacts` | **новая** |
| 13 | `xact_age` | |
| 14 | `query_age` | |
| 15 | `change_age` | |
| 16 | `query` | |

Почему именно так:

- `leader` стоит сразу за `pid` — это родственные атрибуты идентичности процесса.
- `backend_xid` → `horizon_xacts` → `xact_age` идут подряд и читаются как связка:
  «писала ли транзакция → на сколько транзакций назад держит горизонт → сколько уже висит
  по времени».
- `query` остаётся последней: это самая широкая колонка, и логика частично видимой
  последней колонки из горизонтального скролла рассчитана на неё.

На PG 10–12 раскладка не меняется — прежние 14 колонок.

### Ключевые компоненты

- **`leader`** — идентификатор группы параллельного запроса: `pid` лидера, если он есть,
  иначе собственный `pid`. То есть у обычного бэкенда и у лидера равен собственному `pid`,
  у параллельного воркера — `pid` лидера. Всегда непустая.
- **`backend_xid`** — идентификатор транзакции. Пуст, пока транзакция ничего не писала.
  Смысл несёт сам факт наличия значения, а не число.
- **`horizon_xacts`** — на сколько транзакций назад сессия держит горизонт xmin. Пуст,
  когда у сессии нет активного снапшота.

### UX-поведение

- **Пустые значения рендерятся пустой строкой, никогда как `0`.** Ноль в `horizon_xacts`
  означал бы «держит горизонт прямо сейчас», а не «не держит вовсе» — это разные состояния.
- **Сортировка по разреженной числовой колонке работает численно** и не зависит от того,
  какая строка оказалась первой. **Пустые значения уходят в конец списка при обеих
  направлениях сортировки** — и по убыванию, и по возрастанию. Иначе при сортировке по
  возрастанию пустые ячейки всплыли бы наверх и смешались с настоящим нулём, что нарушило
  бы правило «пусто — это не ноль».
- **Ширина экрана.** Три новые колонки сдвигают `query` вправо на 38 символов:
  `leader` — 8 (минимальная ширина колонки в проекте), `backend_xid` — 11,
  `horizon_xacts` — 13, плюс двухсимвольный зазор после каждой; ширину задаёт длина имени
  колонки, а не значений. Отдельной митигации не требуется: горизонтальный скролл
  (фича 009) снял ограничение ширины — именно поэтому расширение этого экрана стало
  возможно.
- **Существующие фильтры не конфликтуют.** Фильтр `I` скрывает `idle`, но интересующее нас
  состояние `idle in transaction` под него не попадает. Фильтр `A` (порог возраста) сессию,
  держащую горизонт, пропускает при достаточном возрасте — у неё выставлен `xact_start`,
  по которому этот фильтр и работает.

## Как должно работать

### Основной сценарий

1. Пользователь подключается `pgcenter top` к серверу PG 13 или новее.
2. Система выбирает ветку запроса для PG 13+ и показывает 17 колонок.
3. Пользователь сортирует по любой из новых колонок и читает результат.

### Граничные случаи

- **Транзакция ничего не писала** — `backend_xid` пуст. Это норма для большинства строк,
  а не сбой.
- **У сессии нет активного снапшота** — `horizon_xacts` пуст. Тоже норма.
- **Служебные процессы** (checkpointer, walwriter, bgwriter) на экране не появляются вовсе:
  у них нет ни начала транзакции, ни начала запроса, а существующий фильтр экрана
  сравнивает с порогом именно их. Никакой обработки не требуют.
- **Autovacuum worker** на экране появляется — он выполняет транзакции. `leader` у него
  равен собственному `pid`, `horizon_xacts` может быть непустым. Это корректно: autovacuum
  тоже держит горизонт.
- **Параллельные воркеры наследуют снапшот лидера**, поэтому при сортировке по
  `horizon_xacts` группа займёт подряд N+1 верхних строк с одинаковым значением. Это не
  дефект: `leader` у них общий, и группа читается как одна сущность.
- **Пустой результат** (ни одной строки) — ширины считаются по длине имён колонок,
  сортировка выходит сразу.
- **Wraparound счётчика транзакций** — формула `age()` устойчива к нему по построению.
  Это одна из причин, почему на `activity` выбрана именно она.
- **PG 10–12** — новых колонок нет, экран остаётся 14-колоночным. Сообщения о
  недоступности не показываем: это не «фича недоступна», а просто старая раскладка.
- **PG 9.5/9.6** — соответствующие ветки запроса не трогаются вовсе.
- **Нехватка привилегий** — `pg_stat_activity` не возвращает ошибку, а молча отдаёт NULL по
  чужим сессиям. Ловить нечего; последствие — ложно пустая колонка, см. риски.

## Критерии приёмки

- [ ] На PG 13+ экран `activity` показывает 17 колонок в порядке, зафиксированном выше,
      дословно. Живая проверка — на PG 14–19.
- [ ] На PG 10–12 селектор возвращает прежний запрос и 14 колонок. Проверяется **только**
      табличным юнит-тестом: кластеров этих версий нет в тестовом образе `pgcenter-testing`.
- [ ] `leader` равен собственному `pid` у лидера и у обычного бэкенда, равен `pid` лидера
      у параллельного воркера. Сортировка по `leader` ставит лидера и его воркеров подряд.
- [ ] `backend_xid` пуст у транзакции, которая ничего не писала, и непуст у писавшей.
      Никогда не отображается как `0`.
- [ ] `horizon_xacts` пуст, когда у сессии нет активного снапшота; иначе — неотрицательное
      число транзакций. Никогда не отображается как `0` при отсутствии значения.
- [ ] Сортировка по `horizon_xacts` упорядочивает численно независимо от того, какая строка
      оказалась первой; пустые значения уходят в конец списка при **обеих** направлениях
      сортировки и не смешиваются с настоящим нулём.
- [ ] `report -A` на архиве, записанном до 0.12, воспроизводится байт-в-байт как сегодня.
      Оговорка: это измерено на конфигурации **без** правки сортировки. Правка затрагивает
      общий движок и меняет режим сортировки для любой разреженной колонки на любом экране,
      поэтому эталонные отчёты нужно перепроверить уже с ней.
- [ ] `report -d -A` описывает новые колонки, помечает их как доступные с PG 13+, и содержит
      четыре оговорки: `leader` — это `pid` лидера, если он есть, иначе собственный `pid`
      (а не сырой `leader_pid`, который у лидера пуст); горизонт показан только по бэкендам;
      формула `horizon_xacts` отличается от одноимённой колонки экрана `replication`; и пустая
      ячейка может означать нехватку прав на просмотр чужой сессии, а не отсутствие горизонта.
- [ ] Архив, охватывающий смену версии в середине записи, пересчитывает ширины колонок —
      нет ни устаревшей раскладки, ни падения на нулевой ширине. Проверяется синтетическим
      архивом из двух наборов сэмплов с разными версиями. Ловушка, которую обязан учесть тест: путь воспроизведения
      пропускает первый замер новой версии, поэтому после смены версии в архиве должно быть
      **не меньше двух** замеров — иначе тест окажется зелёным на пустом отчёте.
- [ ] Тест запросов `activity` проверяет против живого сервера на всех доступных версиях
      (PG 14–19) **имена колонок и их порядок**, а не только факт «запрос не падает».
- [ ] Порядок строк описания новых колонок в `report -d -A` зафиксирован тестом.
- [ ] В реестре техдолга заведены записи про: мёртвый `internal/stat/help.go`; расхождение
      формул одноимённой колонки `horizon_xacts` на двух экранах; расхождение между
      порт-картой тестов и составом тестового образа для версий ниже PG 14.
- [ ] `make test`, `make lint`, `make vuln` — зелёные.

## Ограничения

- **Экран отвечает на вопрос «кто держит горизонт» только по бэкендам.** Горизонт держат
  ещё слоты репликации, prepared transactions и standby feedback — их в `pg_stat_activity`
  нет вовсе. Полный агрегат по всем четырём источникам осознанно отложен в backlog релиза.
- **Вводимая граница ветвления 12→13 живьём непроверяема.** В тестовом образе
  `pgcenter-testing` есть только PG 14–19, поэтому ошибка в границе не будет поймана ни
  одной живой проверкой — только табличным юнит-тестом селектора, где граница фиксируется
  с обеих сторон.
- **Совместимость записей.** Формат архивов `record`/`report` менять нельзя: архивы,
  записанные до 0.12, обязаны воспроизводиться как прежде.
- **`horizon_xacts` измеряется только в транзакциях**, без пересчёта во время. Честной
  конверсии дистанции xid во время не существует: десять тысяч транзакций — это три секунды
  на нагруженном OLTP и трое суток на спокойном сервере. Временнóе измерение даёт соседняя
  колонка `xact_age`.

## Риски

- **Риск 1: сортировка по разреженной числовой колонке молча ломается.** Режим сортировки
  выбирается по значению первой строки; у новых колонок большинство ячеек пусты, поэтому
  сортировка недетерминированно проваливается в лексикографическую, где `"9"` больше
  `"1000000"`. Бьёт ровно в главный сценарий. **Митигация:** входит в скоуп фичи — образец
  для выбора режима берётся из первой непустой ячейки колонки, а пустые значения уходят в
  конец списка **при обеих направлениях сортировки**. Покрывается юнит-тестом на разреженную
  колонку.

- **Риск 5: правка сортировки — это изменение общего движка, а не локальная починка.**
  Выбор режима сортировки используется всеми экранами, поэтому правка меняет поведение и там,
  где колонка разрежена по другой причине (например, возраст транзакции у простаивающих
  сессий начнёт сортироваться как длительность, а не как строка). Это исправление, а не
  регрессия, но радиус больше, чем у остальной фичи. **Митигация:** перепрогнать эталонные
  отчёты уже с этой правкой — прежнее измерение сделано без неё.

- **Риск 2: пустая ячейка читается как «горизонт никто не держит».** Причин пустоты три:
  сессия действительно не держит горизонт; горизонт держит источник вне `pg_stat_activity`;
  у пользователя нет прав видеть чужие сессии. **Митигация:** оговорка в описании колонок
  (`report -d -A`). Кода не требует — `pg_stat_activity` при нехватке прав не возвращает
  ошибку, ловить нечего.

- **Риск 3: порядок колонок легко переставить незаметно.** У риска два канала, и оба
  закрываются тестами. Порядок описаний колонок в `report -d -A` — тестом по готовому
  образцу, уже имеющемуся в проекте. Порядок колонок в самом запросе — сверкой имён и их
  последовательности с тем, что вернул живой сервер, на всех доступных версиях.
  **Остаточный риск:** живых кластеров PG 12 и 13 нет, поэтому на них порядок по-прежнему
  держится только на дословной записи в этом документе.

- **Риск 4: смена версии внутри архива оставляет устаревшие ширины колонок.** Фича добавляет
  этому дефекту новую границу (12→13) к уже существующей (9.6→10), а в пути печати отчёта
  нет защиты от нулевой ширины — там это падение, а не косметика. **Митигация:** техдолг
  [021] чинится внутри этой фичи и проверяется синтетическим архивом из двух наборов
  сэмплов с разными версиями.

## Технические решения

- Мы решили назвать колонку **`horizon_xacts`**, а не `xmin_age`, потому что экран
  `replication` уже называет эту величину именно так, и её описание уже есть в `report -d`.
  Один термин на два экрана.

- Мы решили **не показывать сырой `backend_xmin`**, потому что экран `replication` уже принял
  ровно это решение: наружу идёт обогащённая дистанция, сырое значение остаётся внутри
  запроса. Для ранжирования «кто держит горизонт дольше» сырой xmin избыточен.

- Мы решили **оставить `backend_xid`**, потому что он несёт сигнал, которого нет больше нигде
  на экране: транзакция писала или только читала. Колонка `query` этот вопрос не закрывает и
  вводит в заблуждение.

- Мы решили показывать **`leader` как производную величину**, а не сырой `leader_pid`, потому
  что `leader_pid` пуст и у самого лидера тоже — он непустой только у воркеров. Сортировка по
  сырому значению увела бы лидера в общую кучу и не собрала бы группу. Производная колонка
  даёт лидеру и всем его воркерам одно значение.

- Мы решили назвать эту колонку **`leader`**, а не `pgroup`, потому что имя должно читаться
  DBA, который не открывал документацию: во время инцидента её не читают. `pgroup` одинаково
  правдоподобно читается как «process group» — совсем другой unix-термин — и как «parallel
  group». `leader` не пересекается с чужой терминологией, и семантика угадывается без описания.

- Мы решили **оставить сырой `backend_xid`, а не заменять его булевым индикатором**, хотя
  смысл там несёт только наличие значения. `backend_xid` — имя колонки из каталога
  PostgreSQL, DBA знает, что это; синтетическая колонка «да/нет» потребовала бы собственного
  объяснения, а прецедента выдуманных булевых колонок в pgcenter нет.

- Мы решили **принять сдвиг колонки `query` вправо** на 38 символов — ради сигнала,
  который нужен не всем. На узком терминале качественно ничего не меняется: до `query` уже
  сейчас около 115 символов, и она и так уходит за правый край. Реальное ухудшение — на
  широком терминале, где `query` был виден сразу, а теперь может потребовать одного шага
  скролла.

- Мы решили **начать сверять имена и порядок колонок с живым сервером**. Сегодня тест
  запросов `activity` отбрасывает эти сведения и проверяет лишь то, что запрос не падает.
  Фича построена на честном разделении «что реально проверено живым кластером, а что нет»,
  поэтому утверждение «17 колонок в таком-то порядке» не должно оставаться заявлением, когда
  кластеры доступны. Сверка имён вместо одного лишь их количества стоит столько же, но
  дополнительно закрывает риск незаметной перестановки колонок.

- Мы решили **не показывать возраст горизонта во времени** на этом экране, потому что
  единственная формула для этого требует включённого `track_commit_timestamp`, который
  практически никогда не включён. Механизм условного расширенного запроса в коде есть (им
  пользуется экран `replication`), но добавление второго такого экрана удваивает матрицу
  проверок «версия × настройка» ради сигнала, который почти всегда недоступен.

- Мы решили **не переписывать формулу на экране `replication`** под ту, что используется
  здесь, хотя она честнее (не зависит от настройки и переживает wraparound). Это другой
  экран и другая задача; расхождение вместо этого документируется.

- Мы решили **починить выбор режима сортировки и техдолг [021] внутри этой фичи**, потому что
  обе проблемы фича делает достижимыми: первая ломает её главный сценарий, вторая получает от
  неё новую границу смены раскладки.

- Мы решили **не трогать `internal/stat/help.go`**, хотя он оказался мёртвым кодом с
  устаревшими названиями колонок. Это не наша причина; кандидат в реестр техдолга.

## Тестирование

**Unit-тесты:** делаются всегда, не обсуждаются. Ключевые:

- расширение таблицы версий в тесте селектора запроса — граница фиксируется **с обеих
  сторон** (PG 12 на старой ветке, PG 13 на новой). Это единственная защита от ошибки в
  границе 12→13;
- тест сортировки по разреженной числовой колонке;
- апгрейд теста запросов `activity` до сверки имён колонок и их порядка с живым сервером;
- тест порядка строк описания колонок в `report/describe.go`.

**Интеграционные тесты:** делаем частично — синтетический архив из двух наборов сэмплов с
разными версиями для проверки пересчёта ширин. Обратная совместимость воспроизведения архивов
**уже покрыта** существующими golden-тестами и дополнительных не требует: это проверено
прогоном, а не предположением.

**E2E тесты:** не делаем — в проекте нет E2E-контура для TUI, а поведение экрана проверяется
приёмкой на живых кластерах.

## Как проверить

### Агент проверяет

| Шаг | Инструмент | Ожидаемый результат |
|-----|-----------|-------------------|
| 1. Прогон тестов | `make test` | Зелёный, включая новые тесты селектора и сортировки |
| 2. Линт и уязвимости | `make lint`, `make vuln` | Зелёные |
| 3. Совместимость воспроизведения | `go test ./report/...` | Существующие golden-тесты проходят без правок |
| 4. Раскладка колонок | `pgcenter top` на PG 14–19 | 17 колонок в зафиксированном порядке (порядок дополнительно сверен тестом с живым сервером) |
| 5. Держатель горизонта | сессия `BEGIN; SELECT ...;` и простой | `horizon_xacts` непуст, `backend_xid` пуст |
| 6. Писавшая транзакция | та же сессия после `INSERT` | `backend_xid` непуст |
| 7. Группа параллельного запроса | `SET max_parallel_workers_per_gather = 4;` + тяжёлый seq scan | Несколько строк с одинаковым `leader`; у лидера `leader` равен `pid` |
| 8. Сортировка | сортировка по `horizon_xacts` при разреженной колонке | Верный числовой порядок, пустые внизу |
| 9. Описание колонок | `pgcenter report -d -A` | Описания новых колонок, пометка «с PG 13+» и все четыре оговорки |

Стенд: образ `pgcenter-testing` (PG 14–19) — локально либо на чистой ubuntu-24.04.
Поднимается на этапе приёмки.

### Пользователь проверяет

- Общее впечатление от раскладки на своём рабочем терминале — не стало ли читать экран
  тяжелее из-за трёх новых, преимущественно пустых колонок. Это единственное, что нельзя
  проверить автоматически: цена изменения на самом используемом экране pgcenter субъективна.
